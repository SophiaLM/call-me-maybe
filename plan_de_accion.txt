================================================================
     PLAN DE ACCIÓN — call me maybe
     Introducción a las llamadas a función en LLMs
================================================================

Guía completa para implementar function calling con constrained
decoding en Python 3.10+

----------------------------------------------------------------
RESTRICCIONES IMPORTANTES
----------------------------------------------------------------
- PROHIBIDO: dspy, pytorch, transformers, huggingface, outlines
- No usar métodos privados de llm_sdk
- No hardcodear soluciones basadas en los ejemplos dados
- Todas las clases DEBEN usar Pydantic para validación
- El LLM debe elegir la función (no heurísticas)
- Solo se puede usar: numpy, json, pydantic

FLUJO CLAVE:
  prompt en lenguaje natural
    → LLM elige función (constrained decoding)
    → LLM genera argumentos (constrained decoding)
    → JSON válido al 100%

FASE 2 — MOTOR DE CONSTRAINED DECODING (núcleo) (~4-6h)
================================================================

Esta es la parte más importante del proyecto. Invertir aquí
el mayor tiempo.

--------------------------------------------------------------
PASO 2.1 — Explorar el vocabulario del modelo
--------------------------------------------------------------
[CLAVE] Usar llm_sdk.get_path_to_vocabulary_json() para cargar
el vocabulario. Entender la estructura: dict token_id → string.

Tareas:
  → Leer el JSON de vocabulario
  → Construir dos mappings: id→str y str→id
  → Identificar qué tokens corresponden a:
     '{', '}', '"', ':', ',', dígitos, letras, punto decimal
  → Comprobar si hay tokens multi-caracter
     (ej: el token "fn_" podría existir como uno solo)

NOTA: Este paso de exploración es PREVIO a escribir el
constraining. Sin entender el vocab, no se puede hacer bien.

--------------------------------------------------------------
PASO 2.2 — constrained.py — Máquina de estados JSON
--------------------------------------------------------------
[OBLIGATORIO] Implementar una máquina de estados que, en cada
posición de la generación, sabe qué tokens son válidos para
continuar produciendo JSON válido conforme al esquema.

Estados posibles (ejemplo):
  - START              → espera '{'
  - IN_KEY             → generando una clave de objeto
  - AFTER_KEY          → espera ':'
  - IN_VALUE_STRING    → generando valor de tipo string
  - IN_VALUE_NUMBER    → generando valor de tipo number
  - IN_VALUE_BOOL      → espera 'true' o 'false'
  - BETWEEN_FIELDS     → espera ',' o '}'
  - DONE               → JSON completo

Funciones a implementar:
  get_valid_tokens(state, partial_output, schema) → list[int]
    Devuelve los token_ids permitidos en el estado actual.

  mask_logits(logits, valid_token_ids) → logits_masked
    Pone -inf en todos los tokens no válidos.
    (logits es un numpy array o Tensor)

IMPORTANTE: La restricción no es solo JSON sintácticamente
válido. También debe respetar el esquema:
  - fn_name debe ser uno de los nombres disponibles
  - Los valores de args deben ser del tipo correcto
    según function_definitions.json

--------------------------------------------------------------
PASO 2.3 — Loop de generación token a token
--------------------------------------------------------------
[OBLIGATORIO] El proceso central del sistema:

  1. encode(prompt) → input_ids (list[int])
  2. Convertir a Tensor para get_logits_from_input_ids
  3. Aplicar mask_logits según el estado actual del parser
  4. Seleccionar el token con mayor logit (argmax)
  5. Añadir token a input_ids y al output parcial
  6. Actualizar el estado del parser con el token elegido
  7. Repetir desde el paso 2 hasta alcanzar estado DONE

Condición de parada: cuando el JSON está completo
(el parser llega al estado DONE, normalmente al cerrar '}'.

================================================================
FASE 3 — SELECCIÓN DE FUNCIÓN Y GENERACIÓN DE ARGUMENTOS (~2-3h)
================================================================

[OBLIGATORIO] function_selector.py — El LLM elige la función

  El LLM debe elegir qué función llamar.
  NO usar heurísticas: la selección viene del modelo.

  Estrategia:
  → Construir prompt que muestre funciones disponibles:
    "Given these functions: [lista nombres y descripciones],
     which function should be called for: [prompt del usuario]?
     Answer with only the function name."
  → Al generar la respuesta, los tokens válidos son ÚNICAMENTE
    los que pueden formar uno de los nombres de función
    disponibles en function_definitions.json
  → Esto garantiza que fn_name siempre será un nombre válido

  Ventaja: el modelo "elige" semánticamente, pero el constraining
  garantiza que el resultado sea siempre parseable.

[OBLIGATORIO] args_generator.py — El LLM genera los argumentos

  Una vez elegida la función, generar el objeto JSON de args
  usando constrained decoding con el esquema exacto.

  Restricciones por tipo de parámetro:
  → "number"  : solo tokens de dígitos, punto decimal, signo
  → "string"  : cualquier texto válido entre comillas dobles
  → "boolean" : restringir a tokens "true" o "false" únicamente
  → Asegurar que TODOS los parámetros requeridos se incluyen

CONCEPTO CLAVE: CÓMO FUNCIONA EL CONSTRAINING
================================================================

1. Cargar el vocabulario con get_path_to_vocabulary_json()
   y construir un mapa: token_id → string

2. Cuando el LLM va a generar el siguiente token,
   obtener los logits: get_logits_from_input_ids(input_ids)

3. Según la posición actual en la estructura JSON
   (¿esperando nombre de función? ¿valor numérico? ¿clave?),
   calcular qué token_ids son sintácticamente válidos.

4. Poner -inf en los logits de todos los tokens NO válidos.

5. Hacer argmax → el token elegido SIEMPRE es válido.

DOS USOS DISTINTOS en este proyecto:
  - Para fn_name: solo permites tokens que formen uno de los
    nombres de función disponibles (selección viene del LLM)
  - Para args: restringes según el tipo de cada parámetro
    · number  → dígitos y punto decimal
    · string  → texto libre entre comillas
    · boolean → tokens "true" o "false"

Lo más difícil: la máquina de estados del parser JSON y
mapear bien los tokens multi-caracter del vocabulario.
Empezar siempre explorando el fichero de vocab.
