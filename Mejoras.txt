SECTION 1 — BLOCKER: llm_sdk/pyproject.toml missing dependencies
================================================================

PROBLEM:
  llm_sdk/pyproject.toml declares:
    dependencies = []
  but llm_sdk/llm_sdk/model.py does:
    import torch
    from transformers import (
        AutoModelForCausalLM, AutoTokenizer,
    )

  When `uv sync` runs (the ONLY command the evaluator runs), it
  installs ZERO dependencies for llm_sdk. That means torch and
  transformers are never installed. The Makefile tries to fix this
  with `uv pip install torch ...` and `uv pip install transformers`,
  but these run AFTER uv sync and are not guaranteed.

WHY IT MATTERS:
  The program crashes on first import of Small_LLM_Model. This is
  the #1 reason the project does not execute.

FIX — Edit llm_sdk/pyproject.toml:

  [project]
  name = "llm-sdk"
  version = "0.1.0"
  description = "LLM SDK mock for call_me_maybe"
  requires-python = ">=3.10"
  dependencies = [
      "torch",
      "transformers",
  ]

  [build-system]
  requires = ["hatchling"]
  build-backend = "hatchling.build"

  [tool.hatch.build.targets.wheel]
  packages = ["llm_sdk"]

WHY THIS WORKS:
  When uv resolves dependencies, it pulls in torch and transformers
  transitively through llm_sdk. Evaluator runs `uv sync` only, and
  everything gets installed.

TEST:
  rm -rf .venv && uv sync && uv run python -c "from llm_sdk import Small_LLM_Model; print('OK')"

FILES TOUCHED:
  - llm_sdk/pyproject.toml

SECTION 3 — CRITICAL: FunctionNameConstraint never terminates
================================================================

PROBLEM:
  File: src/constrained.py — class FunctionNameConstraint

  The `is_complete()` method:
    def is_complete(self) -> bool:
        return self.generated in self.valid_names

  This only returns True when `self.generated` is EXACTLY one of
  the valid function names (e.g. "fn_add_numbers").

  If the model generates:
  - "fn_add_numbers\n"  (trailing newline)
  - "fn_add_numbers "   (trailing space)
  - "fn_add_numbers."   (trailing period)
  → is_complete() never returns True.
  → generate() loops until max_tokens (200) and returns None.
  → The function is selected as None → WARNING every time.

  With Qwen3-0.6B, this happens OFTEN because small models don't
  reliably generate exactly the function name with no extra chars.

ROOT CAUSE:
  The underlying assumption is wrong: we assume the LLM will
  generate the exact function name and stop. In reality, LLMs
  generate tokens greedily and often add whitespace/punctuation.

FIX — Rework the completion logic:

  Change is_complete() to detect when NO valid name can possibly
  be formed by extending `self.generated`:

    def is_complete(self) -> bool:
        if self.generated in self.valid_names:
            return True
        # If no valid name starts with current generated text,
        # we have gone too far — consider complete (and we'll
        # extract the best prefix below).
        if not any(
            n.startswith(self.generated) for n in self.valid_names
        ):
            return True
        return False

  Also update `generate()` in constrained.py to handle this:
  When constraint.is_complete() returns True but the generated
  string is not in valid_names, find the LONGEST valid prefix:

    # In generate(), after the loop or when constraint.is_complete():
    if constraint.is_complete():
        result = constraint.generated
        if result not in constraint.valid_names:
            # Find longest matching prefix
            matches = [
                n for n in constraint.valid_names
                if result.startswith(n)
            ]
            if matches:
                result = max(matches, key=len)
            else:
                # Try suffix matching (model may have prepended text)
                matches = [
                    n for n in constraint.valid_names
                    if n in result
                ]
                if matches:
                    result = max(matches, key=len)
                else:
                    return None
        return result

  This ensures the generation terminates cleanly even when the
  model is imprecise.

ALTERNATIVE (simpler):
  Change FunctionNameConstraint to stop as soon as generated text
  matches a valid name PREFIX but the next token cannot continue
  any valid name:

    def valid_token_ids(self, id_to_token):
        cache = _get_prefix_cache(self.valid_names, id_to_token)
        valid = list(cache.get(self.generated, frozenset()))
        if not valid and self.generated in self.valid_names:
            # We matched exactly AND no token can extend it:
            # return the EOS/nothing to signal completion.
            pass
        return valid

  And in generate(), treat empty valid_ids + generated in
  valid_names as completion.

FILES TOUCHED:
  - src/constrained.py (FunctionNameConstraint, generate)

SECTION 4 — CRITICAL: ArgsConstraint unknown param types
================================================================

PROBLEM:
  File: src/constrained.py — ArgsConstraint

  In _valid_value_start_tokens() (line 424-445):
    if self.param_type == "string": ...
    if self.param_type == "number": ...
    if self.param_type == "boolean": ...
    return []  # <-- unknown type returns empty → generation fails

  If the function definition uses "integer" instead of "number",
  or any other type not in the three handled, the constraint
  produces zero valid tokens → generate() returns None.

  The spec says types are "number", "string", "boolean", but
  evaluators may add custom functions with other types.

FIX — Normalize types and add fallback:

  Add a normalization step in ArgsConstraint.__init__ or in the
  loader that maps common type names:

    _TYPE_ALIASES = {
        "integer": "number",
        "int": "number",
        "float": "number",
        "double": "number",
        "str": "string",
        "bool": "boolean",
    }

  When param_type is set, normalize it:

    raw_type = self.params[self.current_key].type
    self.param_type = _TYPE_ALIASES.get(raw_type, raw_type)

  Also, for the BEFORE_VALUE state, add a fallback that accepts
  any token (treat unknown type as string) instead of returning
  empty:

    if self.state == "BEFORE_VALUE":
        if self.param_type == "string":
            return self._check_first_char(idx, '"', id_to_token)
        if self.param_type == "number":
            return self._check_multi_char(...)
        if self.param_type == "boolean":
            return ...
        # Fallback for unknown types: accept anything
        return list(id_to_token.keys())

SECTION 5 — HIGH: Performance O(n) forward passes become O(n^2)
================================================================

PROBLEM:
  File: src/constrained.py — generate() (line 185-215)

  Each iteration calls:
    inp = np.array(current_ids, dtype=np.int64)
    logits = model.get_logits_from_input_ids(inp)

  Where `current_ids` grows by 1 each step. So step 1 processes
  1 token, step 2 processes 2, ..., step N processes N tokens.
  Total work: O(N^2) where N is the final sequence length.

  With max_tokens=200, that's 200×99 = ~20K token-processings per
  generation. For 8 prompts × 2 generations = 16 generations,
  that's ~320K token-processings. On CPU with Qwen3-0.6B, this
  takes 20-60 seconds.

ROOT CAUSE:
  The SDK's get_logits_from_input_ids always processes the FULL
  input sequence. transformers supports past_key_values (KV cache)
  to avoid recomputing previous tokens, but the SDK interface
  doesn't expose it.

FIX OPTION A — Modify the SDK to use KV cache (recommended):

  In llm_sdk/llm_sdk/model.py, modify get_logits_from_input_ids
  to accept and return past_key_values:

    def get_logits_from_input_ids(
        self,
        input_ids: np.ndarray,
        past_key_values=None,
        use_cache=True,
    ):
        self._lazy_init()
        if input_ids.ndim == 1:
            input_ids = input_ids.reshape(1, -1)
        inp = torch.tensor(
            input_ids, dtype=torch.long, device=self.device
        )
        with torch.no_grad():
            outputs = self._model(
                inp,
                past_key_values=past_key_values,
                use_cache=use_cache,
            )
        logits = outputs.logits[0, -1, :].float().cpu().numpy()
        return logits, outputs.past_key_values

  Then in generate(), maintain a `past_key_values` variable and
  only pass the NEW token ID (not the full sequence) on subsequent
  steps:

    def generate(model, input_ids, constraint, id_to_token,
                 max_tokens=200):
        current_ids = list(input_ids)
        past_key_values = None
        first_step = True

        for _ in range(max_tokens):
            valid_ids = constraint.valid_token_ids(id_to_token)
            if not valid_ids:
                if constraint.is_complete():
                    return constraint.generated
                return None

            if first_step:
                inp = np.array(current_ids, dtype=np.int64)
            else:
                inp = np.array([token_id], dtype=np.int64)

            logits, past_key_values = model.get_logits_from_input_ids(
                inp, past_key_values=past_key_values
            )
            logits = np.asarray(logits, dtype=np.float32)
            if logits.ndim == 2:
                logits = logits[0]

            masked = mask_logits(logits, valid_ids)
            token_id = int(np.argmax(masked))
            token_str = id_to_token.get(token_id, "")
            if not token_str:
                return None
            constraint.advance_str(token_str)
            current_ids.append(token_id)
            first_step = False

            if constraint.is_complete():
                return constraint.generated
        return None

  This reduces each step from O(N) to O(1) after the first forward
  pass.

  NOTE: The instructions say "Está prohibido usar cualquier método
  o atributo privado del paquete llm_sdk." Modifying the SDK's
  public method signature IS allowed (it's a public API change),
  but using _lazy_init, _model, _tokenizer from the caller is NOT.
  The fix above modifies the SDK itself, which is part of the
  project repo and thus permitted.

FIX OPTION B — Reduce max_tokens (quick win, less impact):

  In constrained.py generate(), reduce max_tokens:
    - FunctionNameConstraint: max_tokens=30 (names are short)
    - ArgsConstraint: max_tokens=100

  In function_selector.py and args_generator.py, pass a smaller
  max_tokens to generate():

    result = generate(
        model, input_ids, constraint, id_to_token,
        max_tokens=30  # for function names
    )

  This reduces worst-case O(N^2) from 200^2=40K to 30^2=900
  (function selector) and 100^2=10K (args generator).

FILES TOUCHED:
  - llm_sdk/llm_sdk/model.py (if Option A)
  - src/constrained.py (generate signature)
  - src/function_selector.py (pass max_tokens)
  - src/args_generator.py (pass max_tokens)

SECTION 6 — HIGH: Performance max_tokens too high
================================================================

PROBLEM:
  constrained.py line 191:
    def generate(..., max_tokens: int = 200) -> Optional[str]:

  Default is 200 for ALL generations. Function names are at most
  30 chars (e.g. "fn_substitute_string_with_regex" = 34 chars).
  Args JSON is at most ~80 chars for simple functions.

  With 200, every failed generation loops 200 times (all 200
  forward passes) before returning None. This is wasted work.

FIX — Set appropriate defaults per use case:

  In constrained.py, keep the default but lower it:

    def generate(..., max_tokens: int = 150) -> Optional[str]:

  In function_selector.py:
    result = generate(
        model, input_ids, constraint, id_to_token,
        max_tokens=50,
    )

  In args_generator.py:
    result = generate(
        model, input_ids, constraint, id_to_token,
        max_tokens=120,
    )

  Also add an early-exit optimization: if the constraint is
  FunctionNameConstraint and generated is already longer than
  any valid name, stop immediately.

FILES TOUCHED:
  - src/constrained.py (default max_tokens)
  - src/function_selector.py (explicit max_tokens)
  - src/args_generator.py (explicit max_tokens)

SECTION 7 — HIGH: filter_vocab strips non-ASCII tokens
================================================================

PROBLEM:
  File: src/constrained.py lines 20-29:

    _ASCII_PRINTABLE = frozenset(string.printable)

    def filter_vocab(vocab):
        return {
            tid: s for tid, s in vocab.items()
            if s and all(c in _ASCII_PRINTABLE for c in s)
        }

  string.printable is:
    '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ
     !"#$%&\'()*+,-./:;<=>?@[\\]^_`{|}~ \t\n\r\x0b\x0c'

  This FILTERS OUT every token containing a non-ASCII character.
  For Qwen3-0.6B (which uses a BPE tokenizer trained on multilingual
  text), this removes a HUGE portion of the vocabulary, including:
  - Tokens with accented characters (é, ñ, ü, etc.)
  - Tokens with Unicode quotes (", ")
  - Tokens with em-dash, en-dash, etc.
  - Many tokens that are perfectly valid inside JSON strings

  More critically, the tokenizer might encode some ASCII characters
  as multi-byte tokens that include non-printable BPE markers
  (like the Ġ U+0120 space marker that the code already normalizes
  in __main__.py). These filtered tokens might be the ONLY way to
  generate certain strings.

WHY IT MATTERS:
  - String arguments containing non-ASCII characters will fail
  - Reduced vocabulary means the LLM has fewer options, but it also
    might mean NO valid token is available for certain positions
  - The Ġ marker filtering was already handled in __main__.py, but
    if tokens containing Ġ also contain other non-ASCII chars they
    get filtered

FIX — More permissive filter:

  Instead of filtering to ASCII printable only, filter to exclude
  only tokens that would break JSON structure:

    import re

    # Only exclude tokens that contain JSON-breaking characters
    # but are NOT just those characters (e.g., a token that is
    # exactly '"' is valid; a token that has an unescaped quote
    # in the middle is problematic)
    _JSON_UNSAFE_RE = re.compile(r'[^\x20-\x7E\n\r\t]')

    def filter_vocab(vocab):
        """Remove tokens that contain control chars (except
        whitespace) or other JSON-breaking content.

        Preserves non-ASCII Unicode so that the model can generate
        strings with accented characters, emoji, etc.
        """
        # Keep all tokens that are non-empty and don't contain
        # ASCII control characters (except \n, \r, \t)
        _CONTROL_CHARS = frozenset(
            chr(i) for i in range(32)
            if chr(i) not in "\n\r\t"
        )
        return {
            tid: s for tid, s in vocab.items()
            if s and not any(c in _CONTROL_CHARS for c in s)
        }

  The critical insight: we only need to remove tokens that would
  break JSON parsing. Everything else (including non-ASCII Unicode)
  is safe inside a JSON string value.

  - src/constrained.py (filter_vocab)

SECTION 10 — MEDIUM: Prompts are weak for a 0.6B model
================================================================

PROBLEM:
  function_selector.py _build_prompt():
    "Available functions:"
    "- fn_add_numbers(a: number, b: number): Add two numbers..."
    "\nWhich function should be called for: '{user_prompt}'?"
    "Answer with only the function name."

  args_generator.py _build_prompt():
    "Generate arguments for function 'fn_add_numbers(a: number, ...)'"
    "matching the request: '{user_prompt}'."
    "Output only a JSON object with the correct arguments."

  Qwen3-0.6B is a 600M parameter model. It does NOT follow
  complex instructions well. The prompts are vague and give no
  examples. The model may not understand what "constrained" output
  means.

WHY IT MATTERS:
  Weak prompts → the model produces wrong function names or wrong
  argument values → the constraint rejects them → generation fails
  → fallback to empty result → accuracy drops below 95%.

FIX — Use few-shot examples and clearer instructions:

  For function_selector.py:

    def _build_prompt(functions, user_prompt):
        lines = [
            "You are a function-calling assistant. "
            "Pick the best function for the request.",
            "",
            "Functions:",
        ]
        for fn in functions:
            params = ", ".join(
                f"{name}: {p.type}"
                for name, p in fn.parameters.items()
            )
            lines.append(
                f"  {fn.name}({params}) — {fn.description}"
            )

        # Add few-shot examples
        lines.extend([
            "",
            "Examples:",
        ])
        has_number = any(
            "add" in fn.name.lower() or "sum" in fn.description.lower()
            for fn in functions
        )
        has_greet = any(
            "greet" in fn.name.lower()
            for fn in functions
        )
        if has_number:
            lines.append(
                'Request: "Add 5 and 10" → fn_add_numbers'
            )
        if has_greet:
            lines.append(
                'Request: "Say hello to Alice" → fn_greet'
            )
        lines.extend([
            "",
            f'Request: "{user_prompt}"',
            "Function:",
        ])
        return "\n".join(lines)

  For args_generator.py:

    def _build_prompt(fn_def, user_prompt):
        params_desc = ", ".join(
            f"{name}: {p.type}"
            for name, p in fn_def.parameters.items()
        )
        return (
            f"Generate a JSON object with arguments "
            f"for {fn_def.name}({params_desc}).\n"
            f"Request: {user_prompt}\n"
            f"The JSON must match this schema:\n"
            + _schema_example(fn_def) + "\n"
            f"JSON:"
        )

    def _schema_example(fn_def):
        """Generate an example JSON for the function schema."""
        example = {}
        for name, p in fn_def.parameters.items():
            if p.type == "number":
                example[name] = 0
            elif p.type == "string":
                example[name] = ""
            elif p.type == "boolean":
                example[name] = True
            else:
                example[name] = None
        return json.dumps(example, indent=2)

  Key principle: shorter prompts with examples work better for
  small models. End with a clear "trigger" phrase like "Function:"
  or "JSON:" that tells the model exactly what to generate next.

SECTION 11 — LOW: ArgsConstraint IN_KEY with shared prefixes
================================================================

PROBLEM:
  In ArgsConstraint._valid_key_tokens() (line 407-422):

    def _valid_key_tokens(self, idx, id_to_token):
        remaining = set(self.params.keys()) - self.completed_keys
        chars: Set[str] = set()
        pos = len(self.current_key)
        for key in remaining:
            if pos < len(key):
                chars.add(key[pos])
        if self.current_key in remaining:
            chars.add('"')
        return self._check_multi_char(idx, chars, id_to_token)

  If two parameters share a prefix (e.g. "source_string" and
  "source_language"), the prefix "source_" is common to both.
  The method correctly generates "source_" and then allows both
  "s" and "l" at position 7.

  HOWEVER: when current_key = "source_", the check
  `self.current_key in remaining` is False (neither "source_" nor
  any key matches "source_"), so `"` (close quote) is NOT added.
  This is correct — you can't close the key mid-way.

  But what if the tokenizer has a multi-character token like
  "source_" as a single token? Then the model generates
  "source_" in one step, and then needs to continue with either
  "s" or "l". The first-char index maps "s" to token IDs starting
  with "s", and "l" to token IDs starting with "l". This works.

  The REAL bug: when current_key + token_str produces a string
  that is NOT a prefix of any remaining key. For example:
  - remaining keys = {"source_string", "source_language"}
  - current_key = "sourc" (typo or tokenizer artifact)
  - No remaining key starts with "sourc" → chars set is empty
  → returns [] → no valid tokens → generation fails.

  This CAN happen if the tokenizer has weird token boundaries.
  For example, token "sour" followed by token "c_" would produce
  "sourc_" which is NOT a prefix of any key, but both tokens
  individually are valid continuations.

FIX — More robust key validation:

  Instead of checking character-by-character against remaining
  keys, check if the proposed continuation (prefix + token_str)
  is still a prefix of any remaining key:

    def _valid_key_tokens(self, idx, id_to_token):
        remaining = set(self.params.keys()) - self.completed_keys
        if not remaining:
            return []
        valid = []
        for tid, token_str in id_to_token.items():
            if not token_str:
                continue
            candidate = self.current_key + token_str
            # Either candidate can be completed to a key,
            # or it IS a key (close the string)
            if any(k.startswith(candidate) for k in remaining):
                valid.append(tid)
            elif candidate in remaining:
                # Allow the closing quote too
                for tid2, s2 in id_to_token.items():
                    if s2 == '"':
                        valid.append(tid2)
                break
        return valid

  This is slower (O(vocab × remaining)) but more correct.
  As optimization, use the prefix cache approach (similar to
  FunctionNameConstraint) but for key names.

  SIMPLER FIX: Add a fallback in _valid_key_tokens: if no chars
  are generated from the analysis, fall back to allowing any
  token that is a prefix of any remaining key (using the existing
  prefix cache infrastructure).

FILES TOUCHED:
  - src/constrained.py (ArgsConstraint._valid_key_tokens)

SECTION 13 — LOW: Writer uses model_dump() pydantic v2 only
================================================================

PROBLEM:
  src/writer.py line 24:
    data = [r.model_dump() for r in results]

  model_dump() is pydantic v2 API. In pydantic v1, it's .dict().

  If the evaluator has pydantic v1 installed, this crashes.

WHY IT MATTERS:
  The pyproject.toml specifies "pydantic" without a version
  constraint. pydantic v1 and v2 have different APIs. The
  project should be explicit about which version it requires.

FIX — Pin pydantic v2 and use compatibility layer:

  In pyproject.toml:
    dependencies = [
        "numpy",
        "pydantic>=2.0",
    ]

  Or use the compatibility helper:
    try:
        model_data = r.model_dump()
    except AttributeError:
        model_data = r.dict()

  RECOMMENDATION: Pin pydantic to >=2.0, since the code uses
  BaseModel from pydantic (which works in both v1 and v2) but
  model_dump() is v2-only.

SECTION 14 — LOW: make install is fragile
================================================================

PROBLEM:
  Makefile install target:

    install:
        uv sync
        uv pip install torch --index-url https://download.pytorch.org/whl/cpu
        uv pip install transformers

  This uses uv pip install (a subprocess) with hardcoded index
  URLs. If torch or transformers change their package index, this
  breaks. Also, `uv sync` should be enough — manual pip calls
  indicate missing dependency declarations.

  Once Sections 1 and 2 are fixed (llm_sdk declares torch and
  transformers), the Makefile install target becomes simply:

    install:
        uv sync
        uv pip install -e llm_sdk

  Or even just:

    install:
        uv sync

  (if llm_sdk is properly declared as a dependency in the root
   pyproject.toml)
